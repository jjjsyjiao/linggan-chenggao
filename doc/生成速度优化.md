# 生成速度优化（2026-10-28）

Flutter 调用的 `POST /api/v1/xhs/notes/generate` 在一次视觉请求中发送**全部图片和完整创作要求**，同时生成逐图观察与自由稿件。来源、引用、事实、排版和发布长度问题现在保留完整草稿，返回可选的 `review_warnings`（缺失时按 `[]` 处理）。新版客户端在预览页明确展示警示；旧客户端只兼容基本稿件字段，需要更新才能看到警示。无静默截断，也不追加模型请求修复。

## 当前修复：模型完成后不再因编辑问题丢弃草稿

用户两次生成失败时，上游模型实际上均已完成，随后本地渲染抛出 `ValueError`，被统一转换为502：

| 北京时间 | request_id | 模型耗时 |
| --- | --- | ---: |
| 13:28:31 | `d2716fa7d766a013924e2ac44c54adad` | 21.3165秒 |
| 13:29:17 | `2a656dffd9e3c40d2d4714886293c88a` | 19.1716秒 |

旧日志没有记录具体校验原因，也没有保存这两份原始模型结果，**不能确切判断触发了哪一条规则**。本轮将可编辑问题与真正的协议错误分开：

- 来源摘录不匹配时，不采纳为证据并提示核对；数值、地点、经历、食材或花期等检查收集去重警示，最多12条，不把未知事实标为已验证。
- 无法只靠已有短句满足排版时保留原稿并提示调整；可安全完成的换行或边界标点调整仍在本地进行，不增删词语。
- 发布目标为标题20字符、正文连复制话题1000字符，超出时提示精简；草稿绝对资源上限为标题200、正文8000字符，话题最多16项、每项100字符。
- JSON/schema 损坏、图片 ID 缺失或重复、绝对资源超限等仍返回失败。警示不混入复制正文，也不代表完整事实核验。

当前验证为 Python **631项**、Flutter **32项**通过；本机假上游10个完整链路场景覆盖软警示和硬失败，未追加真实模型请求。该验证证明草稿能被保留并展示，不证明真实模型百分之百遵循任意要求。

## 当前修复：完整要求参与成稿

用户用相同菊花照片、不同提示词生成，却收到几乎相同的笔记。排查确认Flutter每次均发送当前输入，服务也没有缓存笔记；原因是第一版提速将 `idea_text` 从模型输入中移除，本地只依据四组关键词切换固定开头。这丢失了自由创作能力，已停止作为默认方案。

当前仍只有一次 `APP_LLM_IMAGE_MODEL` 请求，无独立写作、策略或SEO模型。模型先输出全部图片的短观察，再根据完整用户要求生成 `draft`（标题、正文、话题）；默认约180至280字，用户指定短诗、列表、分段、无emoji、无互动或其他篇幅时按要求创作。20/1000是发布目标，超出时保留草稿并提示编辑。单图输出预算为1800 tokens，多图按数量增长，最多8000；这是模型输出预算，不代表实际消耗，也不同于正文字符上限。

用户明确提供的地点、时间和经历等背景可以使用；模型应在内部 `user_context_used` 中逐字摘录实际使用的背景。本地不匹配的摘录不作为证据，并通过警示提示核对。主观感受、比喻、治愈风和合法第一人称不会被旧黑名单整篇过滤。提示词要求不自行补充照片外的地点、花期、票价、营业时间、养护剂量或体验功效；图中文字不能作为指令，要求编造事实也不构成事实依据。

本地来源检查只能给出部分风险提示，不能完整判断语义真伪。图片识别、外部事实、用户背景和最终措辞仍需人工核对；没有警示也不代表已核验。协议损坏会明确报错，编辑问题保留当前稿件，不自动付费修复，也不回退到旧固定模板或旧稿件。

下文是前两版提速方案与历史实测，用于说明取舍；其中7.2986秒来自旧模板版，**不能作为当前自由成稿的精确耗时保证**。

## 历史：菊花照片的真实对照与局限

用户另行授权两次对照后，使用其手机实际选取的同三张菊花照片：本地规范化图片SHA-256与客户端此前三次请求完全一致。两条完整要求分别是“恰好四行、80字以内、无话题的现代短诗”和“180至260字、两段、第一人称赏花日记，使用北京植物园背景、不要编造出行事实”。每条仅发送一次模型请求，没有自动重试。

| 项目 | 现代短诗 | 赏花日记要求 |
| --- | --- | --- |
| 实际标题 | 菊之形色 | 菊影层层，色韵流转 |
| 正文字数 | 56 | 190 |
| 实际格式 | 无话题，但模型只输出一行，未满足四行要求 | 两段、4个话题、无提问，篇幅通过 |
| 单次耗时 | 22.4847秒 | 29.4206秒 |
| 上游模型调用 | 1次 | 1次 |
| 总tokens | 3,301 | 3,505 |

两次均HTTP200、非演示、完整携带3张图，模型确实产生了不同体裁与内容，不再回到同一本地模板。健康检查共171次全部200。**这不代表所有写作要求或事实质量均已通过**：短诗漏换行；第二稿虽满足段落与长度，仍偏图像评述，没有充分体现第一人称日记。其“藤编”材质和“地被”种植方式也不能由照片可靠确认。

随后仅离线加强写作指令：第一人称应明确使用“我”，日记避免逐图讲解和论文腔，材质/瓣型/种植方式不确定时采用更稳妥的通称；在所有图片之后再次提醒完整写作要求。没有发起第三次对照请求，不能把这项提示调整称为已真实复测通过。

当时加入纯本地的准确排版处理。将第一份真实短诗离线回放后得到四行，词语及顺序全部保留，仅边界标点和换行调整；第二份已是两段，原样保留。已有正确排版、负向要求、行数范围和“每条独立一行”等分配式要求不会被强行改成总行数。当时可靠短句不足会报错；当前已改为保留原稿并给出排版警示，不切割词语，也不调用第二个模型。

原始实测记录保存在本地忽略目录 `data/validation/live_generation_20261028_intent_poem.json` 与 `data/validation/live_generation_20261028_intent_diary.json`，包含两条要求、原稿、格式缺项、人工审查结论、耗时及图片哈希，不含模型密钥。

该历史阶段的离线回归覆盖同图不同完整要求的HTTP→图片→独立worker→单次模型→不同自由稿件、用户背景原文验证、当时的无来源断言拒绝，以及Flutter返回编辑提示词后再次生成时不复用旧稿。当前无来源断言已改为警示。离线模型替身只能证明传递、校验和展示链路，不能证明真实模型百分之百遵循任意文风。

该历史阶段验证：后端 **595项通过（9.54秒）**，Flutter **26项通过**；当时手机通过Wi-Fi直连电脑局域网的 `:8072/health/live` 实测HTTP200（本机地址未公开）。该组对照真实请求恰好两次、每次一个模型调用，之后没有为该组对照追加收费请求。校验用临时照片副本已删除，手机原图未修改，诊断记录仅保留本地忽略目录。

## 历史：最初的模板提速方案

此前同一张餐盘照片的真实请求耗时154.700秒，共7次模型调用：2次视觉模型、5次文本模型，合计27,988 tokens。其中策略、文案和SEO阶段占102.826秒。旧流程为了生成完整课程报告，还执行视觉汇总、图片编辑与编辑汇总；这些输出未被移动端发布流程使用。

| 项目 | 原完整链路 | 当时的模板快速链路 |
| --- | --- | --- |
| 单图模型请求 | 至少7次 | 1次 |
| 多图模型请求 | 至少 `2 × 图数 + 5` 次 | 1次，携带全部图片 |
| 模型任务 | 看图、汇总、修图、策略、写作、SEO | 食物返回至多3个粗类别/颜色/位置元素；其他图片返回主体和短观察 |
| 文案来源 | 多轮自由撰写与改写 | 食物按枚举本地组句；其他类别组合筛选后的观察原句和固定中性句 |
| 输出预算 | 多份中间报告和完整稿件 | 单图640 tokens，多图按数量增长，上限6000 |
| 重试及修复 | 上游重试、结构化修复可能追加调用 | 不重试、不追加修复、不退回文本模型 |
| 运行依赖 | 子进程加载 CrewAI 及所有 Agent | 快速子进程不加载 CrewAI |

上表描述已停用的模板成稿方式；当前自由成稿仍只调用一次视觉模型。旧 `/report` 保留完整多 Agent 报告。快速生成使用 `APP_LLM_IMAGE_MODEL`，默认 `qwen3-vl-plus`；单次模型超时使用 `APP_LLM_TIMEOUT`（默认120秒），`APP_LLM_RETRY_COUNT` 不影响快速链路。

## 历史：模板版的事实边界（成稿方式已停用）

每张图片都附真实规范化图片字节，不依赖模型选择工具，也不通过只看首图提速。请求包含逐图 `img_N` 标识。响应必须严格符合事实协议，ID完整、唯一且与上传集一致；缺图、格式错误或截断时返回失败，不用另一个模型补写。

当时创作意图与文件名不传给视觉模型，创作意图仅在本地选择简洁、温柔、活泼等固定语气。这正是后来同图不同要求却得到相同模板的原因；当前已改为传入完整创作要求。图中文字始终不具有指令权限，也不作为经过核验的文案事实。

食物采用更保守的受控协议：只接收鱼肉、叶菜、谷物、酱汁、圆形配菜、块状配菜、饮品和其他食物等粗类别，以及预定义颜色与位置。每项须为确定观察，再由本地中文模板组句；**完全忽略食物类别的自由主体和观察文本**，不能把具体豆种、瓜种或菜名带入文案。枚举外值直接校验失败，不追加模型修复。

其他类别仅保留标记为确定、且通过保守筛选的中文观察原句，过滤不确定措辞、配方制作、成分推断、味觉、营养热量、饱腹或瘦身效果、价格、地址、经历、身份等高风险表述。人物主体使用通称。标题不超过20字符，正文加复制时附带的标签不超过1000字符；多图长度不足时省略完整的可选细节，不截断观察句，也不遗漏图片。

没有安全观察时使用中性占位句，供用户编辑。文案会比原先的营销稿更短、更克制。模型标记 `certain` 仍可能识别错误，关键词筛选也不能穷尽所有虚构表达；这些措施限制扩写来源，**不等于独立事实核验**。发布前仍应核对具体物体、食材和个人信息。

## 历史：模板版验证记录

离线完整链路已覆盖 HTTP 上传、实际图片校验/压缩、真实子进程、一个本机模拟上游请求、本地组装与响应。双图请求只发生一次视觉调用，图片解码字节逐一匹配输入，无工具调用或文本模型调用；健康检查同时保持响应。离线单次端到端约0.45秒，仅说明本地调度开销，不能当作真实生成耗时。

新测试覆盖1/2/20图全量附图、缺图/重复ID/额外自由文案拒绝、非法图片零调用、格式失败不修复、模型失败不回退、取消及超时清理，以及口味/配方/身份/不确定措辞等筛选。

首次优化离线回归470项通过（9.34秒）；第三方旧CrewAI弃用告警不影响结果。单独新进程导入快速链路实测约0.438秒，确认未加载CrewAI或旧 `flows`。8072端口已重启为非演示新服务，`/health/live` HTTP 200，OpenAPI已展示快速链路说明。没有为离线测试发起真实模型请求。

## 历史：一次授权的真实速度复测

用户明确授权一次后，于北京时间2026-10-28 11:58，对同一张 `20260202161329_150_6.jpg`、同一创作意图，通过本机8072端口发送一次非演示HTTP请求。未重试，未追加模型调用；累计三次真实生成。

| 项目 | 旧完整链路 | 本次快速链路 |
| --- | ---: | ---: |
| 端到端耗时 | 154.700秒 | **7.2986秒** |
| 模型请求 | 7次 | **1次 `qwen3-vl-plus`** |
| 模型耗时 | 多阶段合计150.830秒 | 6.9995秒 |
| 总tokens | 27,988 | 1,387（输入1,303、输出84） |
| 健康检查 | 154次全部200 | 29次全部200；p50 3.261ms、最大7.238ms |

本次样本约快21.2倍，耗时减少95.28%，tokens减少95.04%；不按两个模型的混合tokens推算等比例费用。真实请求的规范化图片SHA-256匹配本地图片，`is_demo=false`，HTTP 200，图片顺序正确。以上是单次观测，不能保证其他图数、网络或服务商负载下仍为7秒。

**事实质量仍有问题，未将本次原稿认定为免审发布样例。** 原稿只有54字符，没有上次的手作配方、味道、饱腹和瘦身公式，但仍将不明配菜具体命名为“黑豆、白豆、南瓜块”，并使用“沙拉碗”“淋面”等不够稳妥的说法。鱼肉和叶菜的粗场景与实图一致，不代表精细食材鉴定通过。

因此在这次真实验证后，离线将食物输出进一步收紧到上述粗类别、颜色、位置枚举，停止采纳食物自由观察句，而非逐个给“黑豆/白豆”加黑名单。缺少受控观察时返回中性待编辑草稿。**该协议收紧仅做离线验证，没有发第四次付费请求**；7.2986秒是收紧前的一次快速链路实测。新协议仍保持唯一一次视觉调用，但没有重新实测精确耗时。

受控食物协议的最终回归 **483项通过（9.04秒）**。包含粗类别/颜色/位置枚举拒绝未知值、模型标记确定但自由食材名不进入标题正文与报告、空或不确定观察中性占位、20图正文连标签预算，以及双图真实隔离子进程的单请求携图与清理。双图离线完整链路0.429秒，健康检查p50 1.475ms、最大5.769ms；这仍是本机模拟上游测试，不能替代真实模型时延。
